How to Use EPIC

Get your application configured and deploying through EPIC.

Overview

EPIC (Enterprise Pipeline for Infrastructure & Cloud) is PG&E's CI/CD framework built on Azure DevOps. Applications declare their build, test, and deployment intent in a configuration file, and EPIC handles the rest.

The process is simple:

  1. Add a .pipeline/epic.json file to your GitHub repository
  2. Optionally add a .infra/ folder with Terraform configurations for infrastructure
  3. Onboard your app through the + New App button above
  4. Trigger pipeline runs from the app's detail view

The epic.json File

Create .pipeline/epic.json at the root of your repository (or point to it with app.configPath). This file has two sections:

  • app — Your application's identity, source layout, runtime, and tooling
  • cloud — Your deployment target. EPIC supports AWS, Azure, and SAP; the fields you supply depend on the target (see Cloud Targets below)

The app section:

FieldRequiredDescription
app.appNameYesUnique name for your application in EPIC
app.appTypeYesangular, react, dotnet, python, java, go, html, php, ami, cap, btp, or infra
app.codePathNoPath to source code relative to repo root (default: /)
app.infraPathNoPath to the Terraform folder (default: .infra); required for btp
app.configPathNoPath to the .pipeline folder if not at repo root
app.runtimeVersionNoRuntime version override — defaults per appType: angular/react/html/cap 20, dotnet 9.x, python 3.11, java 17, go 1.23, php 8.3
app.scanToolNoCode scan tool (e.g., sonarqube) — enables the Scan App stage
app.buildTestToolNoBuild/unit test runner: karma, jest, vitest, pytest, junit, xunit, gotestsum, phpunit — enables Run Build Tests
app.integrationTestToolNoIntegration test runner (e.g., playwright) — enables Run Integration Tests

The optional tooling fields determine which stages you can select when triggering a run. Run Build Tests, Scan App, and Run Integration Tests are only selectable when buildTestTool, scanTool, and integrationTestTool are set, respectively. Deploy App requires either a .infra/ folder or cloud deployment parameters in your config.

Cloud Targets

EPIC auto-detects your cloud provider from the config — you don't set it directly:

  • appType is btp or cap → SAP
  • otherwise cloud.awsAccountId is present → AWS
  • otherwise cloud.azureSubscriptionId is present → Azure
  • otherwise defaults to AWS

AWS — the most common target:

FieldRequiredDescription
cloud.awsAccountIdYesTarget AWS account ID (12 digits)
cloud.awsRegionNoTarget AWS region (default: us-west-2)
cloud.s3 / cloud.cloudfrontNoSPA targets (angular/react/html) — S3 bucket and CloudFront distribution ID. Auto-filled from your .infra/ Terraform outputs when present
cloud.ec2InstanceId / cloud.appExecutableNoServer targets (dotnet/python/java) — EC2 instance and launch executable. Auto-filled from Terraform outputs when present

When you provision infrastructure through EPIC (a .infra/ folder), the deploy stage reads the Terraform outputs automatically, so the optional deploy fields above are only needed when targeting pre-existing infrastructure. ami apps use a separate set of fields (component recipes, SSM document prefixes) — see the AMI sample.

Azure — App Service deployment:

FieldRequiredDescription
cloud.azureSubscriptionIdYesTarget Azure subscription ID
cloud.azureRegionNoTarget Azure region (default: westus2)
cloud.appServiceNameNoApp Service name to deploy to. Auto-filled from Terraform outputs when present
cloud.resourceGroupNameNoResource group of the App Service. Auto-filled from Terraform outputs when present

SAP — used by btp and cap apps. Credentials are pulled from AWS Secrets Manager, so an AWS account is still required:

FieldRequiredDescription
cloud.awsAccountIdYesAWS account holding the Secrets Manager secret
cloud.awsRegionNoAWS region of the secret (default: us-west-2)
cloud.secretsManager.nameYesSecrets Manager secret name holding the SAP/CF credentials
cloud.secretsManager.keysYesArray of keys to load from that secret as environment variables
cloud.cfApi / cloud.cfOrg / cloud.cfSpace / cloud.cfOrigincap onlyCloud Foundry endpoint, org, space, and identity origin for CAP deployment

Infrastructure (Optional)

If your app requires AWS infrastructure (EC2, S3, CloudFront, Aurora, etc.), add a .infra/ folder at the root of your repository with standard Terraform files:

  • terraform.tf — Backend and provider configuration. Must declare an S3 remote backend (see below)
  • main.tf — Resource definitions
  • variables.tf — Input variables
  • outputs.tf — Output values
  • terraform.auto.tfvars — Variable values

EPIC will automatically detect the .infra/ folder and enable the Infrastructure Deployment option when triggering runs.

An S3 remote backend is required. Your Terraform must include a backend "s3" {} block so EPIC can manage your state. EPIC supplies the backend configuration (bucket, key, region) at init time, so the block can be empty — but it must be present. Without it, EPIC can't manage your state and the Infrastructure Deployment options stay disabled when you trigger a run.

terraform {
  backend "s3" {}
}

SAP BTP Infrastructure

Set app.appType to "btp" to provision SAP Business Technology Platform infrastructure (subaccounts, entitlements, Cloud Foundry environments) with Terraform. BTP is infrastructure-only — it provisions the BTP estate; it does not build or deploy an application.

FieldRequiredDescription
app.appTypeYesMust be "btp"
app.infraPathYesPath to the Terraform files (must contain <appName>.tfvars)
app.configPathNoPath to the .pipeline folder if not at repo root
cloud.awsAccountIdYesAWS account holding the Secrets Manager secret
cloud.secretsManager.nameYesSecrets Manager secret name containing the BTP credentials
cloud.secretsManager.keysYesKeys to load (typically BTP_USERNAME, BTP_PASSWORD, CF_USER, CF_PASSWORD)

How BTP runs differ from standard apps:

  • Only the infrastructure (Terraform) stage runs — Build, Deploy, and Integration Test do not apply
  • Secrets are loaded from AWS Secrets Manager and sourced into every Terraform step
  • terraform fmt and terraform validate always run; Run Linting Tool additionally runs tflint, and Run Tests runs terraform test (both only on an Apply)
  • Infrastructure provisioning is mandatory — BTP always runs Terraform even without a detected .infra/ folder

SAP CAP Applications

Set app.appType to "cap" for SAP Cloud Application Programming model apps. Unlike BTP, CAP builds and deploys an application: EPIC compiles your CDS models into an MTA archive and deploys it to a pre-existing Cloud Foundry space. CAP apps do not provision infrastructure.

FieldRequiredDescription
app.appTypeYesMust be "cap"
app.codePathNoPath to the CAP project (must contain mta.yaml; default: /)
cloud.awsAccountIdYesAWS account holding the Secrets Manager secret
cloud.secretsManager.nameYesSecrets Manager secret name containing the Cloud Foundry credentials
cloud.secretsManager.keysYesKeys to load (typically CF_USER, CF_PASSWORD)
cloud.cfApiYesCloud Foundry API endpoint (e.g., https://api.cf.us11.hana.ondemand.com)
cloud.cfOrgYesCloud Foundry organization
cloud.cfSpaceYesCloud Foundry space to deploy into
cloud.cfOriginYesIdentity provider origin used for Cloud Foundry authentication

How CAP runs work:

  • Build installs the SAP toolchain (@sap/cds-dk, mbt), runs cds build --production, and produces an .mtar archive
  • Deploy pulls Cloud Foundry credentials from Secrets Manager and runs cf deploy into your target org/space — the space must already exist
  • Build Tests, Scan, and Integration Tests are available when their tools are set; there is no infrastructure stage
